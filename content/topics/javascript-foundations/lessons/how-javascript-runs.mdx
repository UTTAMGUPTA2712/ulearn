JavaScript is single-threaded. There is exactly one call stack, and only one
thing runs at a time. Almost every "weird" behaviour people report — a `setTimeout`
that fires late, a loading spinner that never appears, a promise that resolves
"out of order" — comes from not having a model of that one thread.

## The call stack

The call stack is a list of function calls that are currently in progress. When
you call a function, a frame is pushed onto it. When the function returns, the
frame is popped.

```js
function greet(name) {
  return `Hello, ${name}`;
}

function main() {
  const message = greet("Uttam");
  console.log(message);
}

main();
```

While `greet` runs, the stack is `[main, greet]`. When it returns, the stack is
`[main]` again. That is the whole mechanism — and it is why a stack trace reads
bottom-up: the bottom frame is where things started.

If a frame never returns, nothing else can run:

```js
while (true) {
  // The page is now frozen. Clicks queue up but never get handled.
}
```

## The task queue

Browsers and Node hand off slow work — timers, network requests, file reads — to
the host environment, not to your thread. When that work finishes, the host
pushes a **callback** onto a queue. It does not interrupt you.

The event loop has one rule:

> When the call stack is empty, take the next callback from the queue and run it.

"When the call stack is empty" is doing all the work in that sentence. This is
why the following logs `1, 3, 2`:

```js
console.log(1);
setTimeout(() => console.log(2), 0);
console.log(3);
```

`setTimeout(..., 0)` does not mean "run now". It means "you may queue this after
0ms" — and the queue is only drained once the current script finishes.

## Microtasks jump the line

Promises do not use the same queue. They use the **microtask queue**, which is
drained completely after each task, before the next one starts.

```js
console.log("script start");

setTimeout(() => console.log("timeout"), 0);

Promise.resolve().then(() => console.log("promise"));

console.log("script end");
```

Output:

```txt
script start
script end
promise
timeout
```

Both callbacks were queued during the same synchronous run, but the microtask
queue is emptied first. This ordering is specified, not incidental — you can
rely on it.

The practical consequence: a long chain of promises that resolve immediately
will starve timers and rendering, because microtasks keep the loop from moving
on. `await` in a tight loop over 100,000 items is not "async" in any useful
sense; it is still blocking your one thread.

## Why this matters in real code

A common bug looks like this:

```js
setLoading(true);
const result = expensiveSynchronousWork(); // blocks for 2 seconds
setLoading(false);
```

The spinner never appears. `setLoading(true)` schedules a re-render, but the
browser cannot paint until the call stack empties — and it does not empty until
after `setLoading(false)`. The fix is to yield to the event loop, or to move the
work off the main thread with a Web Worker.

## What to remember

- One thread, one call stack. Nothing else runs while a function is running.
- Timers and I/O are handled by the host, then queued as callbacks.
- Microtasks (promises) run before the next task (timers) — always.
- "Async" means "queued later", not "runs in parallel".
