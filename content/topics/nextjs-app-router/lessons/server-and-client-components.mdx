In the App Router every component is a **Server Component** unless you say
otherwise. That default is the single most important thing to internalise,
because it inverts the habit most React developers built up over a decade.

## What each one can do

A Server Component runs on the server, during the render, and never ships to the
browser:

```tsx
// app/topics/page.tsx — no directive needed
import { db } from "@/lib/db";

export default async function Page() {
  const topics = await db.topic.findMany();
  return <ul>{topics.map((t) => <li key={t.id}>{t.title}</li>)}</ul>;
}
```

Note the `async`. You can `await` directly in the component body — no `useEffect`,
no loading state, no client-side waterfall. The database client, the SQL query
and any secrets stay on the server; only the resulting HTML crosses the wire.

A Client Component opts into the browser with a directive at the top of the file:

```tsx
"use client";

import { useState } from "react";

export function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

You need `"use client"` for anything that touches: `useState`, `useEffect`, event
handlers (`onClick`, `onChange`), browser APIs (`window`, `localStorage`), or
most third-party UI libraries.

## The rule that actually matters

`"use client"` marks a **boundary**, not a single file. Every module imported by
a Client Component becomes part of the client bundle too.

So this is expensive:

```tsx
"use client"; // ← at the top of your layout

export default function Layout({ children }) { ... }
```

Everything below it is now client code.

And this is cheap:

```tsx
// app/layout.tsx — stays a Server Component
import { ThemeToggle } from "@/components/theme-toggle"; // this one file is "use client"

export default function Layout({ children }) {
  return (
    <>
      <header><ThemeToggle /></header>
      {children}
    </>
  );
}
```

**Push `"use client"` down to the leaves.** An interactive button should be a
Client Component; the page that contains it should not.

## Passing Server Components through Client Components

A Client Component cannot *import* a Server Component — but it can render one
passed as `children`. This is the escape hatch for wrappers like providers,
modals and tab panels:

```tsx
// Server Component
<ClientCarousel>
  <ExpensiveServerRenderedSlide />
</ClientCarousel>
```

`ClientCarousel` handles the interactivity; the slide is still rendered on the
server. Only the resulting element tree is sent, not the slide's code.

## Props must be serializable

Anything you pass from a Server Component to a Client Component is serialized.
Strings, numbers, plain objects, arrays, `Date`, `Map`, `Set` and JSX all work.
Functions and class instances do not:

```tsx
// ❌ Error: functions cannot be passed to Client Components
<ClientThing onSave={() => db.save()} />
```

The intended way to send behaviour to the client is a Server Action, not a
function prop.

## Choosing, in practice

Start every component as a Server Component. Reach for `"use client"` only when
you hit one of these:

| Need                                    | Component type |
| --------------------------------------- | -------------- |
| Fetch data, read secrets, query a DB     | Server         |
| Render markdown, format dates, heavy libs| Server         |
| `useState`, `useReducer`, `useContext`   | Client         |
| `onClick`, `onChange`, `onSubmit`        | Client         |
| `window`, `localStorage`, `IntersectionObserver` | Client |

## What to remember

- Server is the default; `"use client"` is the exception.
- The directive creates a boundary — everything imported beneath it ships.
- Keep the boundary as low in the tree as possible.
- Pass Server Components as `children` to get past the import restriction.
- Props crossing the boundary must be serializable.
